# دليل المحاسب للنظام المالي الموحد

## نطاق النظام

هذا النظام يجمع محاسبة الشركة، استيراد ملفات Hunger/FTR وKeeta وAmazon، ربط معرفات السائقين والبدلاء، احتساب مستحقات السائق، الرواتب، العملاء والموردين والمصروفات والمخزون والبنوك والضريبة والأصول والميزانيات في كيان سعودي واحد وعملة أساس SAR.

لا يُعد رفع ملف منصة قيداً محاسبياً ولا راتباً. التسلسل الصحيح هو: رفع مشفر، قراءة وتطبيع، حل المشاكل، مطابقة الإجماليات، اعتماد الملف، احتساب الراتب، اعتماد الراتب، تجهيز الدفع، ثم إثبات التسوية المؤكدة.

## تجهيز النظام أول مرة

1. إنشاء الكيان القانوني والسنة والفترات المالية.
2. إنشاء دليل الحسابات والأبعاد المطلوبة: المنصة، الفرع، السائق، السكن، المركبة، المشروع ومركز التكلفة.
3. إنشاء Posting Profile فعال بتاريخ بداية وربط كل Event Code بحساب مدين ودائن. واجهات العمليات لا تختار حسابات التحكم مباشرة.
4. إعداد العملات وأسعار الصرف والرموز الضريبية.
5. إعداد حسابات المنصات والعملاء والموردين والبنوك.
6. إعطاء المستخدم دور `Accountant`. يمكن للمحاسب الواحد الإعداد والاعتماد والترحيل والإقفال، وكل انتقال محفوظ في سجل غير قابل للتعديل.
7. وضع مفتاح تشفير الملفات في إعداد آمن خارج المستودع، واختبار النسخ الاحتياطي والاستعادة.

## ملفات المنصات المعتمدة

- Amazon/ANOW: ملف الدفع الشهري.
- Keeta pay-per-order: ملخص الشركة والسائقين.
- Keeta segments/freelancer: ملخص الشريك وملخص السائقين فقط. لا تُحوّل ورقة تفاصيل الطلبات الكبيرة إلى صفوف خام في قاعدة البيانات.
- Hunger/FTR: ورقتا WR وRLVL فقط للحسابات والمطابقة.

في فحص ملف Keeta segments الكبير تم، بناءً على طلب المالك، فحص رأس ورقة التفاصيل وعينة أول سجل فقط، ولم تُقرأ كل صفوف التفاصيل التي تقارب 162,873 صفاً. إجماليات الاعتماد مأخوذة من أوراق الملخص. المحلل التشغيلي يستخدم القراءة المتدفقة ولا يحمل المصنف كاملاً في الذاكرة.

## رفع ملف منصة ومراجعته

1. ارفع الملف من المسار المباشر المناسب: `/api/accounting/platform-imports/amazon` أو `/hunger` أو `/keeta/pay-per-order` أو `/keeta/segments`. أرسل الكيان والمنصة والفترة والملف، ولا ترسل قالباً أو بصمة أو adapter.
2. النظام يتحقق من الامتداد والتوقيع والحجم، يحسب SHA-256، يشفر الملف، ويرفض تكرار نفس الكيان/المنصة/المحتوى.
3. راجع المشاكل المفتوحة: تغير القالب، معرف غير معروف، بديل مبهم، صلاحية Keeta ناقصة، تكرار مقياس أو فرق إجمالي.
4. عالج المشكلة بسبب واضح. لا يمكن اعتماد دفعة فيها مشكلة Blocking أو فرق مطابقة.
5. في شاشة المحاسب اعرض الحقول العربية الجاهزة: `statusNameAr` و`metricNameAr` و`categoryNameAr` و`messageAr` و`codeAr`، مع إبقاء `metricCode` و`code` للتكاملات. كل صف مندوب مرتبط يعرض `riderIqamaNo` و`riderNameAr`؛ ويبقيهما النظام فارغين فقط عند عدم وجود تطابق مؤكد أو في ملخص الشركة.
5. الاعتماد لا ينشئ راتباً أو قيداً تلقائياً.

## معرف السائق والبدائل

الربط الفعال بتاريخ النشاط يطبق بالترتيب:

1. تعديل المحاسب على سطر الاستيراد قبل الاعتماد.
2. خريطة `PlatformWorkerIdentity` بتاريخ بداية ونهاية.
3. بديل الشفت المسجل في النظام.
4. Hunger disability/substitution.
5. تاريخ Working ID.
6. Working ID الحالي للسائق.

كل خريطة يجب أن تحدد المنصة، المعرف الخارجي، السائق الحقيقي، تاريخ البداية، تاريخ النهاية الاختياري والسبب. تداخل خريطتين فعالتين لنفس المعرف ممنوع. إذا عمل شخص بمعرف شخص آخر، لا تُغير بيانات المصدر؛ أنشئ ربطاً مؤرخاً أو تعديل سطر مع حفظ المعرف الأصلي وسلسلة المصدر.

## سياسة مستحقات السائق

لا توجد أسعار منصات مفعلة Hard-coded. ينشئ المحاسب نسخة سياسة بتاريخ بداية ونهاية ويجربها قبل التفعيل. النسخة المستخدمة تُحفظ داخل مسير الراتب، لذلك لا تؤثر سياسة جديدة في شهر مقفل.

مثال Hunger المطلوب:

- من 0 إلى 499 طلباً: عدد الطلبات × 4 SAR.
- من 500 طلب فأكثر: 2,000 SAR + عدد الطلبات الزائد عن 500 × 6 SAR.

حالات الاختبار الحدية هي 0 و499 و500 و501 و600. ويمكن إعداد Amazon كراتب ثابت 2,000 SAR، وKeeta كمكافأة 500 SAR عند 600 طلب مقبول فأكثر. تطبق سياسة كل منصة منفردة ثم تجمع المكونات في مسير شهري واحد للسائق.

القواعد المسموحة فقط: مبلغ ثابت، مبلغ للوحدة، حد، شرائح/أساس مع زيادة، نسبة، نطاق، سقف، أرضية وشرط أهلية. لا يسمح بكود أو SQL أو تعبير حر.

## الخصومات والقروض

تسجل العناصر المالية بنوع واتجاه وحساب تحكم وأولوية وتاريخ استحقاق. تشمل السلف والقروض والأقساط والمخالفات والإقامة ومكتب العمل والتذاكر والسكن والاكسسوارات وقطع الغيار والبنزين.

تطبق الخصومات حسب الأولوية، ولا ينخفض صافي الدفع تحت الصفر. المتبقي يُرحل للشهر التالي. التصحيح اليدوي سطر موجب أو سالب منفصل مع سبب وملاحظات وملف إثبات؛ لا يتم تعديل المكون الآلي.

## دورة راتب السائق

1. إنشاء المسير للفترة.
2. الاحتساب من دفعات منصات معتمدة وغير مستبدلة وسياسات فعالة.
3. حل صلاحية Keeta أو تسجيل Override مسبب.
4. مراجعة مكونات المنصات والبدلات والمكافآت والخصومات والأقساط والترحيل.
5. اعتماد المسير؛ ينشأ قيد استحقاق ذري مع حالة المسير وسجل التدقيق وOutbox.
6. تجهيز Bank أو Cash أو Hold أو Mixed.
7. البنك يتطلب IBAN سعودي صحيح. النقد يُقسم حسب السكن، ولا يستطيع موزع السكن تأكيد إلا السائقين المصرح لهم.
8. قيد الدفع لا ينشأ عند التجهيز أو التصدير؛ ينشأ عند تأكيد التسوية فقط.
9. العكس يتم من الوحدة نفسها ويرجع أرصدة العناصر والأقساط والترحيل مع عكس القيد في معاملة واحدة.

## المحاسبة التشغيلية

- العملاء: إنشاء فاتورة، إصدار، ضريبة مخرجات، قبض، توزيع ومنع تجاوز الرصيد.
- الموردون: فاتورة، تسجيل، ضريبة مدخلات، دفع، توزيع ومنع تجاوز الرصيد.
- المصروف: يربط بملف مشفر عبر File ID ويقبل أبعاد السائق/السكن/المركبة/مركز التكلفة عند الترحيل.
- المخزون: الاستلام والإصدار والتحويل والتسوية؛ الإصدار والتحويل يستخدمان قفل SQL ويمنعان المخزون السالب.
- البنك: الحساب وكشف البنك والمطابقة مع المستند المالي.
- الضريبة والأصول والميزانيات: الأساس موجود، لكن التفعيل الإنتاجي ينتظر الوحدات المتقدمة المبينة في حالة التنفيذ.

## الفترات والعكس والإقفال

- `Open`: يسمح بالترحيل.
- `SoftClose`: مراجعة ومنع الأعمال العادية حسب السياسة.
- `Closed`: لا يسمح بترحيل أو تعديل مستند نهائي.
- Payroll Lock وTax Lock يمنعان الوحدة المعنية حتى لو كانت الفترة مفتوحة.

المستند المرحل لا يُعدل ولا يُحذف. التصحيح بعكس الوحدة مع السبب ثم مستند صحيح جديد. إعادة الفتح تتطلب سبباً وتسجل المستخدم والوقت. يجب إنهاء قائمة المطابقة قبل الإقفال: المصدر، الرواتب، AR، AP، المخزون، البنك، الضريبة وميزان المراجعة.

## قواعد الأمان اليومية

- أرسل `Idempotency-Key` مختلفاً لكل أمر مالي منطقي، وأعد نفس المفتاح فقط عند إعادة المحاولة بنفس المحتوى.
- لا ترسل مسار ملف. استخدم `/api/accounting/files` واربط `StoredFileId`.
- لا تعتمد رابط `/uploads`؛ المسار محجوب قبل Static Files.
- راجع Correlation ID في المستند وOutbox عند فشل عملية مترابطة.
- لا تعتبر VAT/ZATCA جاهزة للإنتاج قبل اختبار مواصفات ZATCA الحالية في Sandbox واعتماد مستشار ضريبي مرخص.
